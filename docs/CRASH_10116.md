# Crash follow-up: H1Z1.exe.10116.dmp

## Result

The v13 test build still crashes. Its image trampoline is intact in this
snapshot. This dump does not establish the root cause or justify another
trampoline-lifetime fix. No runtime changes were made during this analysis.

## Exception

- Input: `/tmp/H1Z1.exe.10116.dmp` (5,408,810,018 bytes).
- Process ID: 10116; exception thread ID: 10884.
- Exception: `0xc0000005`, parameter 0 = 8 (execute access violation).
- Exception address, RIP, and RAX: `0x280f6f676`.
- RSP: `0x15e980`; RCX: `0x15e978`.
- Memory information marks the target as `MEM_FREE / PAGE_NOACCESS`, outside
  every loaded module.
- The qword immediately below RSP, at `0x15e978`, is also `0x280f6f676`.
  This is consistent with a consumed stack transfer target; it does not
  establish the last executed instruction or the writer of that value.
- Dump timestamp minus process creation timestamp is 194 seconds. This is
  process age at capture, not necessarily time spent in gameplay.

The earlier analysis of PID 10996 documented a **read** access violation at
`H1Z1.exe+0x1bea5a0`. This is a different immediate failure signature; it
could still have a shared upstream cause.

## Control-flow observations and limits

Scanning aligned qwords from exception RSP to the captured stack end
(`0x160000`) found no pointers into the proxy image. This is a raw stack
scan, **not** a verified unwind and not proof the hook had no earlier effect.

The bad address equals `0x140000000 + 0x140f6f676`. The latter is an address
inside H1Z1 containing a jump to `0x140f0637f`. A duplicated image-base addition
is therefore an investigation lead, not an established diagnosis or a safe
address correction.

A nearby stack value below RSP is `0x1414991b6`. The code there restores
registers and traverses game-image jump blocks ending at `0x142133947`, which
advances RSP and jumps through `[RSP-8]`. This is compatible with a stack-based
control transfer, but the dump does not prove that this path produced the
exception. Stack candidates must not be presented as an actual call trace.

## Supplied executable and log follow-up

The supplied executable is 82,158,616 bytes, SHA-256
`5f5a4922b0671e4ed8fd415e753be096ef7a17e360ae80e025f11544c8db9261`.
This exactly matches the supported client in
`electron/services/client-build.ts` (`1.0.326.439939`). Its preferred image
base matches the loaded base, and its PE base-relocation directory is empty.

The log contains 1,252 lines for PID 10116. The v13 worker starts at
21:19:20.514 UTC, and installation succeeds at 21:19:49.727 UTC with
`camera=disabled` and the same trampoline address as the dump. The final
entry is at 21:22:11.673 UTC. No FATAL, failure, or refusal entry occurs in
that run. There are no log lines from exception thread 10884; logging is
selective, so this does not prove the thread never called the hook.

Raw comparisons show 44,651,053 differing bytes in the first on-disk `.text`
section and 3,705,940 in the second. Many disk bytes become structured jump
instructions in memory. This is consistent with runtime unpacking or code
transformation, rather than a simple loaded-image comparison. It is not
evidence by itself that the file is corrupt or that the crouch patch made
those changes. The code near all earlier candidate addresses differs too.

## Stronger candidate for the final transfer

The loaded game image has an absolute pointer `0x140f6f676` at
`0x140f545e8`. The block at `0x140dfb775` reads another qword at
`0x1411627b8`, whose value is `0x140000000`, then adds these operands:

```asm
0x140dfb775  mov rax, [0x1411627b8]   ; 0x140000000
0x140dfb77c  add rax, [0x140f545e8]   ; + 0x140f6f676
0x140dfb783  mov [rbp], rax
0x140dfb787  mov rax, [rbp]
0x140dfb78b  lea rcx, [rbp+0x70]
0x140dfb78f  sub rcx, 8
0x140dfb793  mov [rcx], rax
0x140dfb796  mov rbx, [rbp+0x40]
0x140dfb79a  lea rsp, [rbp+0x60]
0x140dfb79e  mov rbp, [rsp]
0x140dfb7a2  lea rsp, [rsp+8]
0x140dfb7a7  lea rsp, [rsp+8]
0x140dfb7ac  jmp qword ptr [rsp-8]
```

With entry RBP inferred as `0x15e910`, this produces the exact exception
RIP/RAX (`0x280f6f676`), RCX (`0x15e978`), RSP (`0x15e980`), restored RBX
(`0x9e8a9af0`), restored RBP (`0x2d90000`), and both stored target values
at `0x15e910` and `0x15e978`. A direct jump at `0x1410a691b` targets this
block. This is substantially stronger evidence than the earlier nearby
stack-address hypothesis.

The read-only verifier checks the exact block bytes and eight consistency
conditions against the supplied dump; all pass:

```sh
python3 scripts/verify-crash-10116.py /tmp/H1Z1.exe.10116.dmp
```

This remains a reconstruction from one snapshot. It does not prove which
instructions previously executed or which writer supplied the operands.
It does not establish that either operand individually is corrupt, whether
this block should have been reached, or whether the hook had an earlier
indirect effect. Blindly removing the addition would be unjustified.

## Next evidence needed for a fix

The executable and matching log have now been supplied and checked. The
remaining question requires a controlled reproduction or live execution
capture: how the game reaches `0x140dfb775`, and when the qwords at
`0x1411627b8` and `0x140f545e8` acquire these values. Record the user activity
that reproduces the crash. A known-good runtime snapshot of the same build
would also let us compare these transformed code/data locations.

No runtime patch was changed. Do not mask the exception, subtract an image
base from arbitrary targets, or claim that v13 has fixed the crash.

## Controlled comparison prepared

A separate diag1 package now offers an explicit control run (crouch scanner
and detours off) and a v13 hook run, both with read-only polling of the two
operands, candidate transfer code, and animation entry. See
[diag1 instructions](CRASH_DIAGNOSTIC_DIAG1.md). The normal native build
excludes this diagnostic code, and its executable section was verified to
match the existing v13 DLL byte-for-byte.

Additional backward tracing found game-image immediate references to
`0x140dfb775` at `0x140d53f27` and `0x141349c6a`. The former participates in
a conditional stack-transfer sequence; the latter in another stack-transfer
sequence. This confirms there are multiple potential entry paths and does
not identify which one executed. No operand writer was established.

The comparison is intended to determine whether the same failure also occurs
without crouch scanning/detours and whether the suspect operand combination
is already present before hook installation. An identical pre-install
combination would weaken the claim that those operands were changed by the
hook, but would not explain why the code reached the failing transfer.
A single stable control run cannot prove causality.
